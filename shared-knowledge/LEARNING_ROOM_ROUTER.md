## 用途

這是所有學習聊天室共同讀取的公用檔案。使用者不需要逐一告知每個聊天室該學什麼；聊天室必須先依本檔辨識自己的專線，再讀對應 checkpoint 與模組範圍後續接研究。

## 強制讀取順序

1. `shared-knowledge/SHARED_RESEARCH_MASTER_MAP.md`
2. **本檔 `shared-knowledge/LEARNING_ROOM_ROUTER.md`**
3. `research/stock_market_learning_tracker_v0_1.json`（226模組、learningScope、L0-L5與完成度的機器權威）
4. 自己專線的 dedicated checkpoint / research files
5. `RESEARCH_ENGINEERING_GOVERNANCE.md`、`RESEARCH_CHECKPOINT.md` 與需要的 System 1 / System 2 bridge

## 全域學習聊天室強制運作規則

以下規則適用於本專案所有學習相關聊天室與自動學習執行環境，包括 01～11 專屬研究室、AUTO 輪動學習執行室，以及 00｜研究總控室中適用的治理／回覆規則。

1. **所有回覆固定附台北日期時間**
   - 每次對使用者可見的回覆，結尾固定加上：`YYYY/MM/DD HH:MM（台北時間）`。
   - 不因聊天室、研究領域、手動研究、自動輪動、錯誤回報或一般治理回覆而省略。
   - 00｜研究總控室雖不執行專科研究，仍必須遵守本時間格式。

2. **深度且連續研究，不得完成小子題就立即停止**
   - 01～11 專屬研究室與 AUTO 輪動學習執行室，每次開始研究後，必須在同一輪內持續推進，不得只完成一小段、單一文獻、單一例證、單一小子題或單一 commit 就立刻停止並要求使用者再次輸入「繼續」。
   - 正常停止點必須至少符合其中之一：
     1. 已完成一個可辨識的**大段落／完整研究階段**，並已把 durable progress（可持久進度）、證據、反證、PIT、可重播性、資料品質、冗餘、成本、System 1／System 2 增量價值與 exact next continuation point 寫回正式紀錄；
     2. 遇到**必須由韓哥做決策**的重大事項，例如 Formal Core（正式核心）、正式策略規則、正式權重／門檻、系統架構重大變更、Production（正式環境）、Live（實盤）、資金／風險重大調整；
     3. 遇到 MFA、Secret、額外授權或所有安全可行替代方案均已嘗試仍無法排除的真正阻塞。
   - 若工具／額度／外部來源造成被迫中斷，必須先保存 checkpoint，寫清楚本輪做到哪裡與 exact next continuation point；下一輪直接續接，不得重頭研究。
   - 研究過程應持續做正向機制與反向證據／失效條件驗證，不得只蒐集支持原假設的資料。

3. **發現可優化系統的有效新知，必須主動通知韓哥**
   - 若研究得到新知識／新因子／新判讀／新風控方法，且經過正反兩面驗證、PIT／可重播性檢查、資料品質、冗餘、成本與過擬合風險檢查後，判定對 System 1 或 System 2 具有**可驗證的增量價值**，研究室不得只把結果寫進 checkpoint 後繼續埋頭研究。
   - 必須主動通知韓哥，至少說明：
     - 學到了什麼；
     - 支持證據與反證／失效條件；
     - 為什麼可能對現有系統有增量幫助，而不是重複既有因子；
     - 預期改善哪個具體問題／指標；
     - 主要風險、成本與可能副作用；
     - 建議的 Shadow（影子）、OOS（樣本外）或其他驗證方式；
     - 是否已達 `FORMAL_OPTIMIZATION_CANDIDATE`（正式優化候選）門檻。
   - 最後把「是否進行正式優化／Promotion（升級）」交由韓哥決定。未取得批准前，Formal Core 永久 LOCKED，不得自行部署或改變正式交易／選股行為。

4. **00｜研究總控室例外**
   - 00｜研究總控室只負責治理、進度、路由、成熟度、跨線整合與 System 1／System 2 研究銜接，不自行執行 D01～D18 專科深度學習。
   - 因此第 2 條的「持續深度學習」不要求 00 自己做專科研究；但第 1 條時間格式、第 3 條優化候選通知與治理責任仍適用。

5. **後續補充**
   - 韓哥未來新增的全域學習規則，應優先追加到本節；若與其他舊規則衝突，以較新的明確規則為準，並同步修正衝突內容。

## 全域研究執行時間稽核規則

本規則適用於 01～11 所有專屬研究室的手動研究與自動學習排程，用於判斷每一輪研究是否實際持續執行、執行多久，以及是否發生非正常中斷。時間一律使用 Asia/Taipei（台北時間）。

### 1. 開始學習前必須先顯示開始時間

只要即將開始一輪實際研究／學習，在進入研究內容之前，第一個可見的執行標記必須先顯示：

`【本輪開始】YYYY/MM/DD HH:MM（台北時間）`

不得等研究完成後才回填開始時間；不得以聊天訊息送出時間、排程預定時間或 last_run_time 代替實際本輪開始時間。

### 2. 正常完成必須顯示結束時間與本輪耗時

正常完成一輪研究時，原有【學習進度】footer 保留，並在最後追加：

- 本輪開始：YYYY/MM/DD HH:MM（台北時間）
- 本輪結束：YYYY/MM/DD HH:MM（台北時間）
- 本輪耗時：依開始與結束時間計算

最後一行仍固定為：
`YYYY/MM/DD HH:MM（台北時間）`

若工具／環境只能可靠取得到分鐘，耗時以分鐘為最小單位，不得虛構秒數精度。

### 3. 非正常中斷也必須留下時間戳與續接點

若研究因工具錯誤、執行逾時、連線中斷、額度／任務限制、外部來源失效、GitHub 寫入衝突、執行環境終止，或任何非預期原因無法完成正常研究階段，必須在能恢復回覆時明確標示：

`【非正常中斷】`
- 本輪開始：YYYY/MM/DD HH:MM（台北時間）
- 中斷確認：YYYY/MM/DD HH:MM（台北時間）
- 已持續時間：依可驗證時間計算
- 中斷原因：<真正阻塞原因；UNKNOWN 時就寫 UNKNOWN，不得猜測>
- 最後完成點：<最後一個已確定完成且已保存的研究步驟>
- GitHub／checkpoint 寫回狀態：<已寫回／未寫回／UNKNOWN>
- 下一續接點：<exact next continuation point>

非正常中斷不得只顯示「仍在思考中」「仍在執行」或憑畫面狀態推定未中斷。

### 4. 不得用跨數小時的 UI「思考中」狀態當作持續執行證據

ChatGPT UI 顯示「思考中」、轉圈、手機／電腦版狀態不同步、聊天室未更新，都不能單獨證明研究仍在持續執行。

判斷某輪是否仍連續執行，必須依可驗證的工具活動、任務 run 狀態、GitHub／checkpoint 寫回、或其他正式執行紀錄。若缺乏可驗證證據，狀態必須寫 UNKNOWN 或視為待確認，不得對韓哥宣稱「沒有中斷」。

若開始時間與下一個可驗證活動之間出現異常長空窗，且無任何可驗證連續執行證據，必須把該空窗視為可能中斷，回報實際已知時間點，不得把整段牆鐘時間（wall-clock time）都算成有效研究時間。

### 5. 自動學習排程同樣適用

01～11 的自動學習任務每次真正開始研究時，也必須遵守相同開始／結束／中斷時間規則。排程預定觸發時間不等於實際研究開始時間；若任務延遲啟動，必須記錄實際開始時間。

### 6. 與既有學習進度 footer 的關係

本規則不取代既有【學習進度】footer。正常研究回報的結尾順序應為：

1. 【學習進度】
2. 本輪開始
3. 本輪結束
4. 本輪耗時
5. 最後一行日期＋台北時間

若為非正常中斷，則使用【非正常中斷】區塊，仍須保留可取得的學習進度、最後完成點與 exact next continuation point。


## HARD OUTPUT GATE（強制輸出閘門）｜裸英文零容忍

本節優先於其他「英文後附中文」的較寬鬆描述。適用於 01～11 所有手動研究與自動學習回覆。

### 核心規則

研究回覆在送出前，必須完成第二次語言掃描。除明確允許的 machine literal（機器原樣字串）外，**可見文字中不得存在任何未立即附中文解釋的英文單字、英文縮寫、英文品牌名或英文專有名詞**。

這不是「一個英文片語最後補一次中文」；韓哥要求的是**每個英文單字後面都必須有中文解釋**。

正確：
- `Forecast（預估） Freshness（新鮮度）`
- `Consensus（共識） Accuracy（準確度）`
- `Historical（歷史） Validation（驗證）`
- `Quality（品質） Shadow（影子驗證）`
- `Volume（成交量） Profile（分布）`
- `Common（共同） Support（支撐）`
- `Persistence（持續性） State（狀態）`
- `PIT（時點一致性）`
- `OOS（樣本外驗證）`
- `GitHub（程式碼託管平台）`
- `Cloudflare（雲端網路服務商）`

不合規：
- `Forecast Freshness（預估新鮮度）`
- `Consensus Accuracy（共識準確度）`
- `Volume（成交量） Profile（分布）`
因為前面的英文單字沒有逐字緊接中文。

### Machine literal（機器原樣字串）例外

以下內容不可破壞原字串：
- GitHub 路徑與檔名
- URL
- commit SHA
- 程式碼
- JSON key
- 函式名
- 資料欄位名
- 正式模組 ID
- 正式 status code／enum value
- 測試名稱或資料庫 key

這些字串必須用反引號包住，並在**整個原樣字串後**立即加中文解釋。例如：

`LONG_BLOCK_STAGE_VII_COMPLETE`（長區塊第七階段完成狀態）
`SOURCE_BLOCKED`（資料來源阻塞）
`D08-03`（D08 第 03 模組）

不得為了逐字翻譯而改寫 machine literal（機器原樣字串）本身。

### 送出前兩階段掃描

研究室完成草稿後必須執行：

**Pass 1（第一輪掃描）：結構合規**
- 檢查開始時間、固定執行指令、研究內容、Dxx 進度條、各 Dxx 重點、全體進度、整體重點、學習進度、結束時間與耗時。

**Pass 2（第二輪掃描）：英文零裸字**
- 掃描所有可見文字中的 A–Z／a–z 拉丁字母。
- 若字母屬一般英文文字：每個英文單字後立即補中文。
- 若屬 machine literal（機器原樣字串）：用反引號包住並在整串後補中文。
- 掃描後若仍存在未被允許的裸英文，**禁止送出，先修正再重新掃描**。

### 特別禁止

不得因為英文很多、技術內容很長、進度區塊繁複，就降低此規則。
不得只在第一次出現時翻譯、後續同一詞改成裸英文。
不得把「整個英文片語後補一個中文」當成逐字合規。
不得以「使用者懂英文」為理由省略中文。

### 合規判定

只要任一一般英文字詞沒有緊接中文解釋，該輪即為：
`LANGUAGE_GATE_FAIL`（語言閘門失敗）

即使研究內容、GitHub 寫回、進度條、成熟度與時間格式全部正確，也不得稱為完全合規。


## 全域研究啟動指令強制顯示規則

本規則是在既有所有研究治理、時間稽核、學習進度、反證、PIT／OOS／Shadow、GitHub checkpoint、Formal Core LOCKED 等規則之外追加，不取代、不刪除任何既有規則。

適用範圍：01～11 所有專屬研究室的手動研究與自動學習排程。00｜研究總控室與 AUTO 控制器若只做治理／排程、不執行專科研究，則不需偽造此研究啟動指令。

### 1. 每輪開始研究前，必須先顯示固定啟動指令

每一輪只要真正要開始進行專科研究／學習，必須依序顯示：

`【本輪開始】YYYY/MM/DD HH:MM（台北時間）`

接著立即顯示：

`【本輪執行指令】進行深度研究學習與反證，長段落研究模式，依總控規則執行，每個英文單字後面都必須加上中文解釋`

顯示完上述開始時間與固定啟動指令後，才能進入本輪研究內容。

### 2. 此固定啟動指令屬強制執行要求

固定啟動指令代表本輪至少必須同時遵守：
- 深度研究學習，不得只完成零碎小題就停止。
- 正向機制與反向證據／失效條件必須並行。
- 採長段落研究模式，直到完成一個可辨識的大段落／完整研究階段，或遇真正阻塞。
- 依 00｜研究總控室、最新 GitHub main、Router、tracker、專屬 checkpoint 與治理規則續接，不得自行重頭研究。
- 所有可見研究文字中的英文術語、英文縮寫與英文專有名詞，後面必須立即加上中文解釋。

### 3. 英文＋中文解釋的執行方式

一般可見研究文字中，只要出現英文單字、英文縮寫或英文專有名詞，必須立即補中文解釋，例如：
- PIT（時點一致性）
- OOS（樣本外驗證）
- Shadow（影子驗證）
- Market（市場） Regime（狀態）
- Moving（移動） Average（平均線）
- Factor（因子） Redundancy（冗餘）

為避免破壞機器可讀內容，GitHub 路徑、檔名、URL、commit SHA、程式碼、JSON key、資料欄位名稱、函式名、正式模組 ID 等 machine literal（機器原樣字串）必須保留原文；若需要說明，應在其後另加中文解釋，不得改寫原始字串本身。

### 4. 與時間稽核規則的順序

正常研究啟動順序固定為：
1. 【本輪開始】＋實際台北時間
2. 【本輪執行指令】＋固定指令全文
3. 正式研究內容
4. 【學習進度】
5. 本輪開始／本輪結束／本輪耗時
6. 最後一行日期＋台北時間

若發生非正常中斷，仍依既有【非正常中斷】規則顯示中斷確認時間、已持續時間、最後完成點、寫回狀態與 exact next continuation point（精確下一續接點）。

### 5. 合規判定

任何 01～11 研究室若進入實際研究內容，但缺少「【本輪開始】」或「【本輪執行指令】」其中之一，視為該輪未完整遵守研究啟動規則；不得事後以聊天印象補稱已遵守。


## 全域規則

- 聊天室先辨識自己的名稱；只研究被分配的 Dxx 領域。
- **00｜研究總控室身分鎖定**：`00｜研究總控室` 是本專案的 canonical（正式）總控聊天室名稱與治理身分。即使 ChatGPT UI 自動產生、重命名或顯示其他聊天標題，也不得改變其正式角色；只要該聊天室承擔總控職責，即一律視為 `00｜研究總控室`。總控室只負責18大領域／226模組總覽、成熟度、研究依賴、聊天室路由、排程、自動化治理、System 1／System 2 研究銜接與跨線整合，不自行取代專科研究室深挖。
- **00｜研究總控室禁止學習執行**：若使用者在 `00｜研究總控室` 貼入 A／B／C 輪動學習指令、任何 D01～D18 專科研究指令，或要求「繼續學習／深入研究」，總控室不得直接執行專科研究、不得產生新研究證據、不得升級模組成熟度、不得寫入任何專屬 research/checkpoint。總控室只能辨識正確研究線、檢查路由與進度、修正分工，並把工作留給對應研究室或既有自動輪動任務執行。

## 專屬研究室排程建置協定

本節用來處理 ChatGPT Plus 同時最多 5 個 Active Tasks（啟用中排程）的限制，適用於 01～11 專屬研究室建立自己的自動學習排程時。

- 固定保留「全球持股雷達 15分」、「收盤前進出場雙向掃描」與「研究室排程輪動控制器」三個啟用名額；研究室同時最多只保留 2 個 Active。
- 01～11 各研究室仍各自擁有自己的專屬自動學習排程，讓研究輸出回到自己的聊天室；未輪到者一律保持 paused（暫停）。
- 當韓哥在某研究室輸入「建立這個研究室的自動學習排程，依總控規則執行」而目前已達 5 個 Active 時，不得直接回報「名額已滿」後停止。必須執行以下安全交換流程：
  1. 先讀取目前所有 task automations。
  2. 僅從標題以 01～11 開頭且含「自動學習」的 Active 研究室任務中，暫停 1 個以騰出名額；禁止停用任何股票監控、提醒或「研究室排程輪動控制器」。
  3. 在當前研究室建立它自己的專屬自動學習排程。
  4. 建立成功後立即把「新建立的研究室排程」設為 paused，避免破壞當下輪值。
  5. 重新啟用步驟 2 暫停的原研究室任務，使 Active 組合恢復原狀。
  6. 再次驗證總 Active 數不得超過 5，且固定保留 2 個股票監控＋1 個輪動控制器＋最多 2 個研究室。
- 以上交換只用來「建好但先暫停」01～11 專屬任務；真正啟用哪兩個研究室，由「研究室排程輪動控制器」在每小時整點統一切換。
- 專屬研究室排程的固定觸發分鐘採錯峰：01、03、05、07、09 固定每小時 `:10`；02、04、06、08、10 固定每小時 `:35`；11 固定每小時 `:20`。這可確保控制器整點切換後，本小時的研究任務才開始執行，並降低同時寫 GitHub 的 SHA 衝突。所有研究室排程一律使用 exact_schedule（精確排程），不得使用 flexible_schedule（彈性排程）破壞輪值時窗。
- 若建立／暫停／恢復任一步驟出錯，必須主動重試並驗證；禁止因 5-task 上限而要求韓哥手動刪除或搬移研究內容。
- 研究室排程建立完成後，不得把研究內容集中回 AUTO 或總控室；研究內容必須留在各自 01～11 聊天室。

## 全域研究回報末尾：合併版進度總結強制格式

本規則是在既有【學習進度】footer（結尾區塊）、研究開始／結束時間稽核、非正常中斷、固定研究啟動指令等規則之外追加；不取代、不刪除任何既有規則。

適用範圍：01～11 所有專屬研究室的手動研究與自動學習排程。只要本輪有實際研究／學習成果、反證、阻塞、成熟度狀態更新、GitHub 寫回或續接點更新，末尾必須顯示「合併版進度總結」。

### 1. 第一區：GitHub 寫回與續接／本輪總控進度

固定標題：

`【GitHub 寫回與續接／本輪總控進度】`

研究室負責的每一個正式 Dxx 領域都要各自顯示，不得只挑本輪有升級者。例如 04 研究室負責 D04＋D05，就要同時顯示 D04 與 D05；09 研究室負責 D12＋D13，就要同時顯示 D12 與 D13。

每個 Dxx 固定包含四項：

1. `Dxx｜領域名稱　xx.x%`
2. 可視化文字進度條
3. 本領域目前最重要的進度／證據／阻塞重點說明
4. 若本輪成熟度沒有提升，仍須說明本輪新增了什麼證據、反證、工程驗證或為何維持原成熟度

### 2. 進度條固定格式

採 20 格文字進度條；百分比文字是正式值，進度條只作視覺摘要。

例：
`████████░░░░░░░░░░░░ 40.0%`

規則：
- 每格約代表 5 個百分點。
- 顯示的 xx.x% 必須使用最新正式 tracker／Shared Master Map 可重建值，不得依感覺估算。
- 小數百分比保留正式來源精度；進度條格數可依最接近 5% 視覺化，不能反過來用進度條推算正式百分比。
- 若正式值為 UNKNOWN（未知），顯示：
  `[ UNKNOWN｜正式進度值待確認 ]`
  不得畫成 0% 空條，也不得把 UNKNOWN 當成未完成或零成熟度。

### 3. 每個 Dxx 進度條下方必須有重點說明

每個進度下方至少顯示一段「重點：」，內容依最新 GitHub main、專屬 checkpoint、研究證據與 tracker 產生，優先說明：
- 本輪新增／完成了什麼；
- 目前主要驗證到哪裡；
- 尚缺哪個證據、資料、前瞻樣本或工程條件；
- 為何成熟度提升或維持；
- 若阻塞，真正阻塞類型是什麼。

禁止只顯示百分比＋進度條而沒有文字說明。

### 4. 第二區：全體研究模組整體進度

在各 Dxx 進度後固定顯示：

`【全體研究模組】`

至少包含：

1. `全體研究模組　xx.x%`
2. 20 格整體文字進度條
3. 「整體重點說明」一段

「整體重點說明」至少要交代：
- 最新 GitHub main 回讀的正式總模組數；
- 目前整體成熟度／完成度來源；
- 本輪對全體進度的實際影響；
- 若只是增加證據完整性、反證、工程驗證、資料契約或 checkpoint，而沒有正式成熟度提升，必須明確說「本輪沒有藉工程完成提高成熟度」或同等明確說法。

整體百分比只能使用 tracker／Shared Master Map 中正式、可重建的整體指標；若當前正式檔案沒有可重建的整體值，必須顯示 UNKNOWN（未知），不得自行平均或猜測。

### 5. 第三區：既有【學習進度】仍強制保留

合併版進度總結不能取代既有【學習進度】。其後仍須顯示：

`【學習進度】`
- 研究室／領域
- 本輪完成
- 當前模組
- Level（等級）
- 成熟度
- 狀態
- 下一續接點

maturityPct（成熟度百分比）、Level（等級）、status（狀態）必須來自最新正式 tracker；不得因視覺化需求自行調整。

### 6. 正常研究回報的固定末尾順序

正常完成時固定依序為：

1. 【GitHub 寫回與續接／本輪總控進度】
2. 各 Dxx 的百分比＋進度條＋各自重點說明
3. 【全體研究模組】
4. 整體百分比＋進度條＋整體重點說明
5. 【學習進度】
6. 本輪開始
7. 本輪結束
8. 本輪耗時
9. 最後一行：`YYYY/MM/DD HH:MM（台北時間）`

### 7. 非正常中斷時

非正常中斷仍須盡可能顯示最後可驗證的各 Dxx 與全體正式進度，但不得假裝本輪已正常完成。其後改用既有【非正常中斷】區塊，包含：
- 本輪開始
- 中斷確認
- 已持續時間
- 中斷原因
- 最後完成點
- GitHub／checkpoint 寫回狀態
- 下一續接點
- 最後日期＋台北時間

若中斷前無法重新讀回最新正式百分比，使用最後已驗證值並清楚標記資料時間；無可驗證值則標 UNKNOWN（未知）。

### 8. 格式範例（僅示意排版，不代表正式進度）

`【GitHub 寫回與續接／本輪總控進度】`

`D12｜衍生品　40.0%`
`████████░░░░░░░░░░░░ 40.0%`
重點：<本輪證據、進度或阻塞重點>

`D13｜國際總經　41.5%`
`████████░░░░░░░░░░░░ 41.5%`
重點：<本輪證據、進度或阻塞重點>

`【全體研究模組】`

`全體研究模組　47.0%`
`█████████░░░░░░░░░░░ 47.0%`

整體重點說明：
<最新 GitHub main 總模組數、整體進度來源、本輪實際影響，以及是否有正式成熟度提升>

上述範例中的 40.0%、41.5%、47.0% 僅用於說明格式；每輪實際回報必須重新讀取最新正式資料，不得沿用範例數值。

### 9. 合規判定

以下任一情況視為未完整遵守本規則：
- 只有百分比，沒有進度條；
- 有進度條，但缺少每個 Dxx 的重點說明；
- 缺少【全體研究模組】；
- 有整體百分比，但缺少整體重點說明；
- 以主觀估計代替 tracker／Shared Master Map 正式值；
- 用 UNKNOWN（未知）當成 0%；
- 為了讓畫面好看而提高成熟度；
- 顯示合併版後省略既有【學習進度】或時間稽核欄位。


## 全域研究回覆送出前合規自檢

本規則用於防止研究室雖已讀取共用規則，但在實際輸出時漏掉固定格式或英文中文註解。適用於 01～11 所有專屬研究室的手動研究與自動學習排程。

每次準備送出任何研究型回覆前，必須先在內部完成一次 compliance check（合規檢查）；不需把檢查過程展開給韓哥，但輸出結果必須符合下列項目。

### 必查清單

1. 開始階段是否已顯示：
   - 【本輪開始】＋實際台北時間
   - 【本輪執行指令】＋固定指令全文

2. 研究內容與末尾區塊中的英文術語、英文縮寫、英文專有名詞，是否都已立即補中文解釋。
   - 例如：PIT（時點一致性）、OOS（樣本外驗證）、Shadow（影子驗證）、Tracker（進度追蹤器）、Volume（成交量） Profile（分布）、alpha（超額報酬）、recovery（恢復／補回）、generation（世代／生成批次）、common（共同） support（支撐區間）、Persistence（持續性） state（狀態）。
   - GitHub 路徑、檔名、URL、commit SHA、程式碼、JSON key、正式欄位名、模組 ID 等 machine literal（機器原樣字串）可保留原文，但若其語意對使用者有必要理解，後方仍應另加中文解釋。

3. 結尾是否完整包含：
   - 【GitHub 寫回與續接／本輪總控進度】
   - 每個負責 Dxx 的正式百分比
   - 20 格進度條
   - 每個 Dxx 的重點說明
   - 【全體研究模組】
   - 整體正式百分比
   - 整體進度條
   - 整體重點說明
   - 【學習進度】
   - 本輪開始
   - 本輪結束
   - 本輪耗時
   - 最後日期＋台北時間

4. 若為非正常中斷，是否已改用【非正常中斷】區塊並記錄中斷確認時間、已持續時間、最後完成點、GitHub／checkpoint 寫回狀態與下一續接點。

5. 所有百分比、Level（等級）、status（狀態）、整體模組數與成熟度，是否來自最新 GitHub main／tracker／Shared Master Map；不得沿用舊畫面、聊天記憶或示意數字。

### 送出條件

若上述任一必查項目未通過，該研究室應先修正輸出再送出，不得明知缺欄仍視為正常完成。

特別規定：只要可見回覆中存在未附中文解釋的英文術語／縮寫，即使其他進度區塊完整，仍視為「格式部分合規、語言規則不合規」，不得標示為完全遵守總控規則。
